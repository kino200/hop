
## DS-HWPX

- 2026-11-15. HOP는 Tauri 2·Rust·TypeScript 구조이며 일반 저장은 HWP 임시 파일 경로다. 포함된 WASM 엔진은 exportHwpx API를 제공한다. 보호 파일의 저장은 기존 staging API를 우회해 native 메모리 암호화로 연결한다. 고정 rhwp 서브모듈 초기화는 필요하지만 상위 소스는 수정하지 않는다.

- 보호 프로세스는 `managed` 레이블의 비영속 WebView 한 개를 사용한다. 일반 `main*` 창의 파일·저장소 권한이 적용되지 않으며 네이티브 다운로드·외부 탐색·새 창, 평문 저장·인쇄·미리보기 명령을 거부한다. UI는 검토한 편집/저장 명령만 제공하고 복사·드래그·브라우저 출력·복구 저장을 차단한다. 일반 창에서 암호문을 선택하면 본문을 읽지 않고 같은 서명 앱의 새 보호 프로세스로 경로만 전달한다.
- HWPX 내보내기 손실 보고서에 손실이 있으면 저장을 거부한다. 매 저장마다 관리앱에 원본 암호문을 다시 인증하고 문서 ID·ACL 보존 암호문만 0600 임시 파일에서 원자 교체한다. 원본 변경·경로 변경·기존 파일 덮어쓰기는 거부하며 실패 시 편집 상태와 원본을 유지한다.
- 실제 포함 WASM의 HWPX 합성/샘플 메모리 왕복·손실 0을 확인했다. Swift 패키지 34개 중 21개 통과·외부 입력 13개 skipped, HOP native 65개 통과·외부 배지 1개 ignored, 화면 174개 통과 및 tsc·Vite 빌드 성공이다. 서명 설치와 실제 앱 시험 결과는 이후 별도로 기록한다.

- 최종 사전 검증. HOP 전체 pnpm test에서 화면 177개, native 67개(외부 배지 1개 ignored), adapter 24개, QuickLook 8개, 상위 경계 40개가 통과했다. macOS의 Linux 전용 7개는 skipped다. clippy -D warnings와 Release 서명 빌드가 통과했고 규약 5 브리지는 사용자 인증으로 root:wheel 0755 설치·해시를 확인했다. 비인가 호출은 상태 1/exit 1로 거부됐다.
- 실제 앱 시험 중 보호 창의 빈 화면을 발견했다. Tauri 2.10.3이 index.html을 tauri://localhost로 축약하지만 탐색 검사가 빈 경로를 거부한 원인이며, 기존 코드에서 해당 주소의 회귀 시험 실패를 확인했다. 시작 화면의 정확한 세 주소만 허용하도록 수정하고 외부·다른 페이지·사용자 정보·포트·쿼리·fragment 거부를 함께 시험한다. 실제 문서 입력·저장 확인은 계속 진행한다.

- 시작 화면 수정본의 실제 UI에서 WebKit 접근성 입력란 노출을 추가로 발견했다. NSView의 hidden/element 설정만으로는 WebKit의 별도 트리가 차단되지 않아 NSWindow와 하위 NSView의 접근성 children을 빈 배열로 고정했다. 서명 재빌드 후 실제 앱에서 창·메뉴만 조회되고 본문·입력란이 사라지는 것을 확인했다. 메뉴의 새 문서 생성은 현재 한글 자동암호화 정책을 통과해 새 문서.hwpx 보호 초안으로 열렸다. 사용자 본문 입력·저장은 대기 중이다.
- 로그인 UI의 아이디 포커스 문제는 시험 계정 값을 접근성 setValue로 지정해 로컬 로그인을 완료했다. 이 UI 포커스 원인 자체를 수정했다고 주장하지 않는다. 설정의 HWPX만 HOP로 지정했고 기존 편집기 선택은 유지됐다.

- 실제 최초 저장에서 기존 배포본과 새 MarkAny 서명본의 Quick Look 확장 Team ID 차이로 macOS 재실행 확인이 표시됐다. 사용자가 열지 않음을 선택한 뒤 HOP 저장을 완료했다. 이전 서명 앱의 컨테이너 권한을 확대하거나 보안 설정을 초기화하지 않았다. 설치된 Quick Look 라이브러리의 암호문 입력은 썸네일 추출 5·PNG/PDF 렌더 2로 거부되고 모든 출력 길이는 0이었다.
- new-auto.hwpx 실제 저장본은 8,450바이트 암호문이며 잠금 배지·원본/기준 사본 해시 보존을 확인했다. testNewExternalHWPXIsEncryptedAndAuthorized 1개가 통과했다. HOP 정상 종료 후 DocumentSafer를 통해 새 HOP 프로세스에서 다시 열었고 본문 표식의 사용자 재확인은 대기 중이다.

- 사용자가 새 HOP 프로세스에서 HOP-AUTO-ENCRYPTION-HWPX 표식의 재열람을 확인했다. 기존 암호문 편집용 사본 existing-working.hwpx를 DocumentSafer 경로로 열었고 본문 입력·재저장을 요청했다.

- HOP 종료 직후 화면 도구의 getAXState가 종료된 프로세스에 재열기 AppleEvent를 보내 LaunchServices -600 알림을 만든 것을 시스템 로그로 확인했다. 제품 충돌 보고서는 없으며 기존 문서를 연 새 프로세스와 strict 서명은 정상이었다. 이후 저장 완료 프로세스의 종료 확인은 NSRunningApplication 메타데이터만 사용하고 종료된 앱에 화면 조회를 보내지 않는다. 이 문제를 제품 코드 오류로 수정하거나 미저장 문서를 종료하지 않았다.

- 2026-11-15 최종 수용 시험 완료. 사용자가 새 문서의 HOP-AUTO-ENCRYPTION-HWPX와 기존 암호문 편집 저장본의 HOP-EXISTING-HWPX-EDIT를 각각 새 HOP 프로세스에서 재열람해 확인했다. 새 문서 자동암호화·기존 암호문 편집/재암호화·잠금 배지와 원본/기준 사본 해시 보존을 확인했다. 기존 저장본은 문서 ID·ACL·정책을 보존했다. 보호 본문의 입력·저장·재확인은 사용자가 직접 수행했다.
- 최종 실제 저장본 두 경로를 지정한 전체 Swift 패키지 시험은 34개 중 23개 통과·외부 입력 11개 skipped·실패 0개이며 기존 정책 호환 시나리오 208개도 통과했다. 시작 주소와 접근성 보완 후 native 68개 통과·외부 배지 1개 ignored, Clippy -D warnings 및 Release 재서명 빌드가 통과했다. 화면 177개·adapter 24개·QuickLook 8개·상위 경계 40개 전체 시험 결과도 유지된다.
- 정리. 시험 계정을 로그아웃하고 HOP/시험 DocumentSafer 프로세스와 로컬 모의 리스너 종료를 확인했다. 시험 앱 LaunchServices 등록을 해제하고 설치된 운영 DocumentSafer를 재등록했다. 기존 Finder HWPX 기본 연결은 별도 SafeUI 개발 빌드로 확인되어 임의 변경하지 않았다. 수용 시험은 DocumentSafer를 명시한 열기 경로다. 미사용 소켓의 외부 삭제는 OS가 EPERM으로 거부해 남겨 두었다. 기존 DocumentEditingServer.start는 같은 소유자의 연결 불가능한 소켓만 검사 후 교체한다. 제품 정책과 승인된 시험 정책은 변경하지 않았고 커밋·push는 하지 않았다.
- 검증 한계. 이번 실제 통합은 macOS ARM64와 승인된 별도 시험 정책의 HWPX 본문 편집 범위다. HWP 바이너리 확장, 전체 HWPX 서식 충실도, Windows/Linux 실행, OS 전체 파일 I/O 추적, 관리자 메모리/스왑 접근 차단, Apple 공증은 검증하지 않았다. 원본 엄격 정책의 미지원 승인·워터마크·감사 의무는 계속 거부한다.
